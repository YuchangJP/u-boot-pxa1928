# BR2 production U-Boot restoration

The stock BR2 U-Boot inside `CT2-Uboot-flasher(1).apk` differs from the
published MA04 source. These changes are deliberately limited to the MA04
build; MA03/BS continues to use the original CP/MSA arrays and mapping.

## Recovered changes

- MA04 early MFP table: append 0x01081002, 0x0254c000 (GPIO148 pull-up),
  0x0258c000 (GPIO149 pull-up) before MFP_EOC. Original BR2 binary has a
  112-byte copy versus 100 bytes on BS.
- BR2 `cp_d2` copies two images into 0x07e00000 (8544 bytes) and
  0x07f00000 (8828 bytes). The original source used 0x06000000 and
  0x07000000 with shorter payloads.
- BR2 `release_seagull` writes 0x000107e0 to 0xd4051084 instead of
  0x00010600. The earlier timeout restoration is retained.
- The `handle_dtb` GPIO148/149 strap branch and MMC/DTB fixups were already
  restored in commit ca9677ca785ddc8dfc0636297786fe3439830413.

## Payload provenance

Both gzip files contain exactly the corresponding bytes from the stock BR2
1-MiB U-Boot. They were gzip-compressed with mtime=0 for reproducibility.

| br2_d2_07f.bin.gz | 0x939b0 | 0x07f00000 | 8828 | a38f9ec65a140e6929ff8b9019015f50ed62306ac6454f5d7a5cb1aa3cf75507 |

For MA04 builds, the Makefile expands gzip files before assembling
`br2_coprocessor_blobs.S`. Host `gzip` is required. The uncompressed .bin
files are generated artifacts and should not be committed.

## BR2 binary fidelity follow-up

The BR2 production firmware stores the embedded images in writable `.data`,
in this order: `07F` (8828 bytes), followed by `07E` (8544 bytes).
An earlier rebuild kept them in `.rodata` in reverse order. PR #2 fixes the
segment and ordering; the raw image bytes remain SHA-256 identical to stock.

The BR2 sensor strap helper at stock file offset `0x9464` is a standalone
100-byte routine. Its return value is **not** a generic bitwise XOR: GPIO149
equal to 1 flips GPIO148 values 0/1, and other GPIO148 values are returned
unchanged. The source now preserves that logic and marks the function
`noinline`. The C compiler emits a 100-byte helper, but not all instructions
are byte-identical to the stock implementation.

The AOSP prebuilt toolchain has been pinned at
`a7bb6f39cd99b2fb26ecc2d3cb984d18cd259d24`:
`aarch64-linux-android-gcc 4.9.x-google 20140827` and GNU ld 2.24.
With that compiler and the stock-MICOM display configuration, the revised
BR2 `u-boot.bin` measures **666112 bytes**, equal to the **666112-byte**
stock valid-image length. Both rebuilt and stock relocation tables start
at `0x9b7a0` and contain 1220 AArch64 RELATIVE entries. However, the
individual bytes and relocation addends are **not yet identical**.
The BR2 firmware images are present at rebuilt offsets `0x93998` (07F) and
`0x95c14` (07E), versus stock offsets `0x939b0` and `0x95c30`.
That is a remaining 24–28-byte placement difference for these payloads.
An identical-offset match percentage alone is misleading because of shifted
sections and PC-relative addresses.

### Optional MICOM panel variation

The disclosed MA04 source also included GPIO195 `get_board_micom()` detection
and additional conditionals in `vx5b1d_init`. These are **absent from the
stock BR2 panel-initialization call sequence**. They are now disabled in the
default stock-oriented MA04 build, but can be re-enabled with
`CONFIG_BR2_MICOM_VARIANT` if a different board revision requires those
specific LCD settings. The MA03 implementation is unchanged.

The MA03/BS image is not affected by the BR2-specific code changes.
With the original toolchain it remains the same 651384-byte size as stock,
with only the build-version/date string region (58 bytes) differing.

## Verification and safety limitations

The user-provided stock BR2 APK, compiler output, and both firmware payload
checksums were compared. Full PXA1928 GCC 4.9 builds succeeded in GitHub
Actions, but **no physical-device boot test has been performed**. A raw
`u-boot.bin` generated by the build is **not** a validated 1-MiB
ready-to-flash image; do not flash it without separately resolving the
packaging/signing requirements and verifying a reliable recovery path.
Firmware image redistribution terms should be reviewed before republishing.
